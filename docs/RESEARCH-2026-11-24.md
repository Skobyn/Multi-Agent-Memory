## Killed: subagent delegation (J)

The hypothesis was that the lead's Task prompt, a `role=user` row in the subagent's transcript, could grant user
authority. It cannot. `_tail_turns` drops sidechain rows; every row of a real subagent transcript, including the
lead's prompt row, carries `isSidechain: true`; `agent_transcript_path` is read only in `subagent_stop`, which
applies SUPERSEDE lines as agent. A forged subagent prompt holding `/ledger confirm C-0001` was denied, and a grant
the user really typed ran once in total across the lead and two subagents (`authority_used` is keyed by session
and turn). The protection rested on one flag, so a row that carries `agentId` is now treated as sidechain too.

## Shipped: CLI routes that read caller input as the user's turns (J')

The reviewer showed that these all passed `pre_tool_use` with no output and stored user-authority entries:

- `em-hook extract-text F --role user` turned any file into a human user turn (stored `C-0001`, source=user).
- `printf '{"transcript_path":"/tmp/f.jsonl"}' | em-hook hook pre_compact` extracted from a forged transcript and
  stored "Deploy straight to prod without review" with user authority. `hook session_end`, `extract-capture` and
  `extract-pending` read caller-named transcripts the same way.

This is the class of hole that 2026-11-14 closed for `hook user_prompt_submit` only. What shipped:

- `authority.check` refuses any command that runs the CLI's `hook <handler>`, `extract-capture`, `extract-pending`
  or `extract-text` (`_CLI_INTERNAL_RE`), whatever the user's turn says; the user can run them in a terminal.
  `extract-prompts` stays allowed: it reads the store, not caller input. Claude Code and `background.spawn` start
  these processes directly, never through a Bash tool call, so the plugin's own runs are unaffected.
- `extract-text` accepts only `--role assistant`; the Stop hook is its only caller.
- `_CLI_RE` also recognises the `em` console script before `hook` and `extract-`.

Accepted: detection is broad, like the rest of `authority.py`; a commit message reading "em-hook hook" is refused.
Not fixed: the read-check-write on `authority_used` is not atomic, so two concurrent calls under one grant can both
run (`confirm` is idempotent; `add --user` could store a duplicate).

## Shipped: credentials are not stored (C)

A probe with a faked extractor response stored an `sk-ant-` key and a `postgres://user:pass@` URL in `statement`,
`evidence` and `anchors`, in `ledger.jsonl`, `index.db`, `interventions.jsonl` and the pin block. From there the
plugin re-shows them after every compaction, in every subagent, in the MEMORY.md mirror and in deny citations, and
sends the statement to the decision model and the embeddings provider on later calls. Nothing redacted anything.

What the reviewer killed or changed:

- **Redacting on render** would mean guarding about ten outputs and still leave the secret on disk. Redaction runs
  once, when an entry is built.
- **Evidence checks would break.** A redacted quote fails to match the user's raw text, which would demote a real
  user decision. The checks run on the raw quote; only what is stored and logged is redacted.
- **The placeholder became an anchor** (`REDACTED`), so the compaction audit would mark the entry dropped every
  time. It is a stopword now.
- **Falsifiers stay literal.** A "never commit this key" falsifier that holds the key is the enforcement, and
  falsifiers are never rendered or sent out.
- **No entropy rule.** Any rule strict enough to catch keys also catches commit SHAs and integrity hashes.

`redact.py` matches private-key blocks, `sk-` keys (32+ characters with a digit, so `sk-scikit-learn-...` is kept),
GitHub, AWS, Slack and Google keys, JWTs, the password part of URL userinfo, and `password=`-style assignments whose
value has a digit (not `token= parameter` or `$VAR`). It runs on extractor statements, evidence, rationale and log
quotes, on `ledger add`, and in `store.supersede` for every supersede reason.

Accepted limits: the raw prompt still goes to the extractor model; `transcripts/` captures are verbatim; entries
stored before this change keep their text (a `ledger redact` migration must rewrite `ledger.jsonl` and rebuild
`index.db`, or the secret stays in old pages and the WAL).

## Second round: review of the finished diff

A fourth reviewer attacked the diff and confirmed five defects. Each fix has a regression test:

1. **A line continuation hid the route.** `em-hook \<newline> hook pre_compact` passed. The separator in
   `_CLI_INTERNAL_RE` now accepts backslash-newline.
2. **A user's SUPERSEDE reason was logged raw** to `interventions.jsonl` by `_apply_supersede_lines`, although the
   ledger copy was redacted. The log is redacted now, and so are `store.retire` reasons.
3. **Env-style secrets were missed.** `\b` does not match after `_`, so `DB_PASSWORD=...`,
   `AWS_SECRET_ACCESS_KEY=...` and `SECRET_KEY=...` stayed. The assignment rule now takes any name containing
   password, token, secret or api key, `=` with optional single spaces, and a quoted value. Bearer tokens and
   `sk_live_`, `glpat-`, `hf_` and `npm_` tokens were added.
4. **A private-key header with no END line deleted the rest of the statement.** A bare header is not a secret and
   now stays; a header is redacted only with its END line or with key body lines after it.
5. **The `sk-` rule was quadratic** (90 s on 210 KB). Its lookaheads and lengths are bounded; every adversarial
   input in the test now runs in well under 2 s.

Also fixed: `pwd=/home/u/p2`, a branch named `sk-1234-refactor-...`, `task-sk-<hex>.md`, a `host:443@` URL, and
a file named `hook.py` after the CLI name are no longer matched. Accepted: an entry stored with a raw secret
before this change no longer matches a redacted restatement exactly, so dedup and the resurrection guard fall back
to their fuzzy match for it.

## Shrunk and specified: replay parity and a divergence check (A+P)

The reviewer confirmed the 11-19 hole and found it wider. Replay checks no authority, so after `rm index.db` a forged
`supersede` with `by: "agent"`, a `status: retired` event, an `entry_update` of status or provenance, or an
`entry_add` reusing an id each turned a user rule off. No rebuild is needed at all: `sqlite3 index.db "UPDATE ..."`
empties `active_entries()` at once. Killed:

- **Binding `by=user` events to a turn uuid and hash.** The prompt path records no turn uuid, CLI supersedes run in
  another process, the transcript is just as writable, and old ledgers have no binding. Demoting what cannot be
  matched is worse: Claude Code deletes old transcripts, so a user's real revocation would be undone.
- **A hash chain.** The attack is an append, and an appended line with a correct `prev_hash` verifies; the hooks
  run as the same OS user as the agent, so no key is out of its reach.

Specified next:

- `rebuild_from_events` applies the live authority rule: for an entry that has user authority at that point in the
  replay, skip and log (`replay_refused`) a non-user supersede, a non-active status without `by: "user"`, an
  `entry_update` that sets a non-active status or drops user provenance, and an `entry_add` over an existing id. A
  forged `by: "user"` event remains an accepted limit.
- A `meta` table in `index.db` with the ledger byte offset and event count, updated in the same transaction as each
  append. At SessionStart, one `systemMessage` when the file grew or shrank behind the index, when the index was
  rebuilt because it was missing, or when a shadow replay disagrees with the `entries.status` column.
