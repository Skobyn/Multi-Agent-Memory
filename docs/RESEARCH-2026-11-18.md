## Shipped: no user prompt goes unextracted, and the gate waits for one in flight (D)

The reviewer confirmed both halves of the race and refuted its scariest form:

- `UserPromptSubmit` is `async: true`. Extraction takes up to 20 s and the agent's first edit can reach PreToolUse
  first. If the user has just said "switch from Postgres to MySQL", the gate denies the MySQL edit on the old user
  decision.
- The user is **not** stuck. The citation tells them to reply `SUPERSEDE <id>: <reason>`. But that costs a
  round-trip and a unit of the deny budget, for a change the user had already stated.
- The advisor does not rescue it. Its prompt says trajectory text never authorizes breaking a user entry, and three
  deny paths never reach it: a Tier 0 trip, an advisor error, and cooldown. Trusting the slice would be forgeable,
  because a fake `[user]:` line can sit inside assistant text.
- **Worse, and not in the proposal:** a prompt skipped as `debounced` (within 20 s of the last run) or `busy` was
  never extracted until compaction or session end. The Stop worker reads only the assistant's reply. A rule stated
  in a quick follow-up went unrecorded, and a revision in it never reached the gate.

The proposed fix was to downgrade a deny to advisory while the newest user turn is unextracted. The reviewer killed
that. It would turn every user rule advisory each time the user typed anything ("ok go"). A failed or killed
extraction would leave the downgrade on permanently. Harness envelopes also fire UserPromptSubmit and are told
apart only by a heuristic. What shipped is fail-closed:

- **Skipped prompts are kept.** A debounced or busy prompt that is not a harness envelope (`looks_injected`) is
  appended to session state `pending_prompts`, newest 8 kept (`extraction.pending_prompts_max`). The next run
  includes them as user turns (`run_incremental(earlier_prompts=...)`). Stop spawns `em-hook extract-prompts
  --session <id>`, which pops them from the store, not from a temp file the agent could rewrite before the worker
  reads it. Pops use `BEGIN IMMEDIATE`, so two drains never get the same prompts.
- **The gate waits and re-checks, and never downgrades.** The running extraction sets `extraction_inflight` to its
  start time and clears it in `finally`. In `GatePipeline._decide`, if a user-authority entry is among the
  conflicts and a marker is fresh (younger than the extraction budget plus 5 s), the gate polls until the run ends.
  The wait is capped by `gate.inflight_wait_s` (8 s) and by 20 s since evaluation began, inside the 25 s hook
  timeout. Then every conflict whose entry is no longer active is dropped. Only a recorded supersession clears a
  conflict, which the extractor writes after its user-evidence checks. A timeout, a failed run or an unrelated
  prompt leaves the deny standing. The status re-check also applies when no run is in flight. That closes the
  smaller window between reading the entries and deciding.

## Shipped: subagent deny handoff to the lead (B)

The reviewer's live probe (Claude Code 2.1.327, `claude -p`, a throwaway plugin) settled the facts:

- PreToolUse inside a subagent carries `agent_id` and `agent_type`. The lead's own calls carry neither.
- SubagentStop `additionalContext` goes to the **subagent** and re-runs it. The probe looped 9 times. It is not a
  channel to the lead, which agrees with RESEARCH-2026-11-14.
- A synchronous PostToolUse hook on the lead's `Agent` call does reach the lead. Its `tool_response` carries
  `agentId` and `agentType`.
- In the probe, the deny reason reached the subagent and it quoted the deny in its report. So the handoff matters
  only when a report leaves a deny out.

Shipped: `gate` and `authority_check` records carry `agent_id`. A new synchronous PostToolUse entry
(`Agent|Task`, 5 s) runs `post_tool_use_agent`. It finds this session's denies for that `agentId` and drops entry
ids the report already names. It tells the lead which remain ("its report does not mention them; check whether it
worked around them"), and logs `subagent_handoff`. Advisories are behind `gate.subagent_handoff_advisories` (off),
because they fire far more often. The model controls none of the text (ids, counts, ledger statements). Accepted
limit: a background subagent returns before it runs anything, so it gets no handoff.

## Fixed: a granted ledger command could store something the user never typed

Idea G was killed. `authority.check` compares the whole normalized invocation, so `--statement` is already bound
(tests at `test_authority.py:61` and `:127`). The reviewer found the real hole next to it. The comparison runs on
text after `shlex` drops the quotes, so shell expansion never enters it. The user typed
`/ledger add --type decision --statement 'Budget is $LIMIT' --user`. The agent ran
`LIMIT=unlimited em-hook ledger add ... --statement "Budget is $LIMIT" --user`. That was granted and skipped the
gate, and the ledger stored "Budget is unlimited" with user authority. Now a granted command is refused if the shell
would expand `$` or a backtick outside single quotes (`authority.expands`), and the agent is told to quote it
exactly as the user did.

## Why A was killed, and what is left of it

`drift.py` (MemTrace addendum) already fingerprints the files in an agent premise's scope. At SessionStart it moves
a premise whose files changed to `unknown_current`, a review item the gate never reads as active. Triggering on
every write would raise a review item on every deliberate edit that acts on the premise. Experience Rot is stale
experience carried across sessions, and session start is the right place to catch it. Three small gaps:

1. `drift.enabled` defaults to `False`, so as shipped none of this runs.
2. `ledger add --type premise --path X` from the CLI stores no fingerprint. Only the extractor does.
3. SessionStart with `source == "compact"` returns the cached pin before `drift_check` runs.
