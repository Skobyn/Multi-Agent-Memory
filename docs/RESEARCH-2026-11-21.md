# Memory research scan and adversarial triage (2026-11-21)

Window: arXiv submissions from 2026-11-17 to 2026-11-19, the newest the export API returns for "agent memory",
"long-horizon agent" and "context compaction". One older paper that earlier notes had not triaged is included.
Sources already cited in earlier RESEARCH notes or in DESIGN.md were skipped. The `/last30` and `/adhd` skills named
in the routine are not installed in this session, so the scan (export API abstracts) and the divergent ideation were
done by hand. Method:

- Six ideas, ranked by enforcement value per line of code.
- The top four were each attacked by an independent read-only reviewer against the code. Two of the reviewers ran
  offline probes.
- All four were killed as proposed. Two of them came back in reduced form, each closing a gap a reviewer showed in the
  code, and those two were built.
- A fifth reviewer attacked the finished diff.

## Shipped: advisory flag on writes into the monitor's own data directory (C, shrunk)

The reviewer killed the hash chain on three counts:

- **The chain anchors nothing.** The hooks run as the same user. Anything the hook can read (a key, the previous
  line's hash), the agent can read too, and an unkeyed chain takes five lines of Python to recompute. `authority.py`
  already says nothing in-process is sound against `python3 -c`.
- **It guards the wrong file.** The gate and the pin block read `index.db`. `ledger.jsonl` is replayed only when the
  projection is empty, so `sqlite3 index.db "update entries ..."` never touches the chained file.
- **It would raise false alarms.** `_append_event` appends with no lock, from hook processes, detached background
  extraction and parallel sessions. Two writers that read the same tail fork the chain.

The reviewer's offline probe of `hooks.pre_tool_use`, against a store holding one user decision, showed what was
actually missing. All of the following passed the gate with **no output at all**:

- `sed -i` rewriting `"source": "agent"` to `"source": "user"` in ledger.jsonl
- `python3 -c "open(L,'a').write(...)"`
- `LedgerStore(...).confirm('D-0001', by='user')` through `python3 -c`
- `pathlib.Path(L).write_text('')`
- Write or Edit on ledger.jsonl

Nothing in the gate knew about the data dir. This is the "advisory flag on writes into the `epistemic/` data
directory" carried since 11-17.

What shipped (`datadir.py`, wired into `pre_tool_use`, `gate.data_dir_flag`, on by default):

- **Which calls are flagged.** Write, Edit, MultiEdit and NotebookEdit whose resolved path is under `cfg.data_dir`.
  Also Bash commands that name the data dir or the store: its absolute path, `epistemic/`, `ledger.jsonl`,
  `index.db`, `interventions.jsonl`, `pinned.md`, `LedgerStore`, `epistemic_monitor.store` or `EPISTEMIC_DATA_DIR`.
  These are plain substrings, because pathlib and store-API writes do not look like writes to the Bash classifier.
- **Reads are exempt.** A command made only of read-only programs (`cat`, `tail`, `grep`, `jq`, ...) with no redirect
  into a file, no command substitution and no in-place flag is not flagged. The check errs toward flagging.
- **The note never denies.** It says the ledger changes only through user-typed `/ledger` commands, SUPERSEDE lines
  and the extractor, so a direct edit is not a recorded change and carries no user authority. It is appended to a gate
  advisory, and a gate deny stands unchanged. Each hit logs `data_dir_write` with the gate's decision, which `/ledger
  audit` can count.
- **The user's own commands are exempt.** A granted `/ledger` command returns before the gate, so it is never
  flagged.

As with the I1 coverage audit, this catches a confused or steered agent. It is not tamper-proofing.

## Fixed: a supersession now keeps the words that authorized it (D, shrunk)

The reviewer's probe found that a successful user supersede of `C-0001` wrote
`{"event": "supersede", "old": "C-0001", "new": null, "reason": "...", "by": "user"}`. The quote that granted user
authority to remove a user constraint was logged only when the check failed and the claim was demoted. When the check
passed, the quote was recorded nowhere, so nothing could show why a constraint stopped being enforced. This is the
same failure 2611.26361 reports: provenance silently dropped at consolidation.

- **Supersede events keep the quote.** `store.supersede` takes `evidence` and `turn_uuid` and records them on the
  event. The superseded entry gets `revoked_evidence`, which survives a rebuild of the projection from the log. The
  extractor passes the supersede record's quote, and a `SUPERSEDE <id>: <reason>` line stores the line itself.
- **A model-named `turn_uuid` must exist.** The extractor stored whatever `turn_uuid` the model wrote, so an invented
  pointer looked real. It is now kept only if it is one of the chunk's turn uuids, for entries and for supersede
  records. Prompt-time turns carry no uuid, so their entries store `""`, which was already the case in practice.
- **`ledger show -v` shows the evidence.** It prints the evidence quote, with `[unverified]` when that applies, the
  turn, and who revoked the entry with the quote they gave.

Nothing reads `revoked_evidence` for a decision. It is for display and audit only.

Not built from D:

- **The advisor feed.** Verbatim surrounding turns next to authority decisions would reopen the role-grounding
  surface that the extractor closes. GrepMem and SCH measure recall, not violation rate.
- **The capture pointer.** Session id plus turn uuid already finds the turn in Claude Code's own transcript or in any
  capture.
- **Linking a reversal to its replacement** (`new` on extractor supersedes). Setting `new` changes the same-scope
  cascade in `_apply_event`: siblings covered by the replacement's paths stay active instead of becoming review items.
  That needs its own look.
- **Merging evidence in `ledger dedupe --apply`**, so that a verified duplicate is not dropped in favor of an
  unverified one. This is still specified.

## Changed: the entailment audit counts "reported as done" as dropped (B, shrunk)

The reviewer showed that the ledger has no completion state (`STATUSES` has none). The extractor also stores only
standing rules ("run pytest before every commit"), which are never finished. A "still open" marker would therefore be
unverifiable for every commitment. It would also push the agent to re-run work that had already run, which is the
redundant execution CompAct-Bench describes. The gate already enforces process order from `tool_history`, which
survives compaction and never reads the summary.

What changed: the entailment criterion's "false" case now also covers a summary that "presents a standing requirement
or commitment as already discharged or no longer applying". So "ran pytest, all green" no longer counts as preserving
"run pytest before every commit", and the entry is re-pinned. There are no new model calls.

## Why A was killed

- **The gate never reads the summary.** The summary row parses as `KIND_COMPACT_SUMMARY`. The extractor, the
  advisor's trajectory slice and the Stop check read only user text, assistant text and tool-use turns. The advisor
  prompt already says trajectory and summary text never authorize breaking a user entry.
- **Where a user rule exists, the gate catches the action anyway.** The gate denies on that rule, and the pin block
  already restates it after the summary.
- **Where no rule exists, the check has nothing to test against.** This is the real leak: a one-off "don't push yet",
  a CLAUDE.md rule, or a missed extraction. The ledger stores lasting rules, not one-off approvals, so "no supporting
  user entry" would be true for almost every real approval. Claude Code's compactor quotes user messages verbatim, so a
  genuine "ok push it" would be flagged as unapproved, inventing a restriction. That is the paper's other, larger error
  class.
- **Quoting the summary is an injection path.** Putting summary sentences into the authoritative pin block would lend
  them its authority.

The reduced form is specified, not built. In `post_compact`, check approval-shaped sentences against the raw user turns
with `evidence_supported`, not against the ledger. Log the unsupported ones as `unsupported_authorization_candidates`
in `compaction_audit` and pin nothing. Build a pin line only if the logged rate is well above the false-positive
rate.
