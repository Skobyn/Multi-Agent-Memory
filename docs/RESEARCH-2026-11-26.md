1. Eight ideas were ranked by enforcement value per line of code.

3. The two survivors were built, cut down to what the reviewers left standing.

## Shipped: calibration cannot loosen a user rule (A)

The reviewer reproduced the hole end to end. With a user decision D-0001 and the decision model at p=0.92, the call
was denied (tau 0.75, uncalibrated floor 0.9). The agent then ran `em-hook ledger label <id> ok` and
`ledger calibrate`, which wrote `{"decision": 0.95}`, and the same call was allowed. None of these commands needs a
grant (`_MARKER_RE` matches none of them), and `selfguard` skips pure ledger CLI calls. A single label was enough:

- Labels were not deduped, so twelve runs on one `tool_use_id` made twelve samples.
- `--min-labels` is an agent-controlled flag, and `--min-labels 1` worked.

What the reviewer cut:

- **`mark-good` is inert.** `quantile_threshold` is read nowhere outside calibration.py.
- **An authority grant on `label` would not close the hole.** A raw write to `labels.jsonl` or `calibration.json`
  is flagged but never denied. The cap below holds whatever route wrote the file.

It also found a false-deny bug next to the hole. `calibrated` was global, so fitting `decision` lifted the 0.9 floor
for every type. A user constraint at p=0.8 went from allow to deny.

What shipped:

- `gate._tau` caps a calibrated tau for a user-authority entry at `enforce_uncalibrated_min_p`. Calibration can
  still tighten a user rule, never loosen it. This adds no false-deny risk, because the uncalibrated gate already
  denies at 0.9.
- Calibration is per type (`_calibrated_for`), on the no-advisor path and in `_held_user_flags`.
- `calibrate` keeps the last label per `tool_use_id`, which also fixes a correction being counted twice. The CLI
  floors `--min-labels` at 12. The bench calls `calibrate()` in-process and is unaffected.

## Shipped: in-process store writes and the rebuild notice (B, shrunk)

The reviewer killed the replay check:

- **The rebuild runs unattended.** `store.py` rebuilds whenever the index is empty, at the next hook. Emptying it
  with `sqlite3 … DELETE` works as well as `rm`.
- **A direct `UPDATE entries` is easier still** and leaves no ledger line. A check on replay alone protects nothing.
- **Nothing can tell a forged event from a real one.** No key, MAC or hash chain survives a same-uid agent with
  Bash: whatever the in-process writer can read, the agent can use.
- **Refusing unmatched events breaks real flows.** CLI `--by user` grants carry no turn uuid, old ledgers lack any
  new field, and Claude Code's transcript cleanup would make a legitimate supersede fail on a later rebuild,
  bringing retired rules back.

It also found the route that matters more: `python3 -c '…LedgerStore(load_config()).supersede("C-0001", None, "x",
by="user")'` returned True, and neither `authority.check` nor `selfguard` saw it.

What shipped:

- `authority.check` refuses a Bash command that runs the `epistemic_monitor` package in an interpreter
  (`python -c`, `python - <<`) and carries a `"user"` literal. `selfguard` flags one that calls a store mutator
  (advisory only).
- When `LedgerStore` replays `ledger.jsonl` into an empty index, it records `index_rebuilt` in project state, which
  the CLI path records too. The next PreToolUse or SessionStart tells the user once. The notice lists every
  replayed event that retired, superseded, demoted or rescoped a user-authority entry, newest first, and is cleared
  only after the hook's output is built.

## Why C was not built

- **A revert is already caught.** After `SUPERSEDE D-0001: moving to MongoDB` and a new entry D-0002 for MongoDB, a
  Postgres edit is denied on D-0002, even with eight entries crowding the budget.
- **The version chain is not in the data.** Both supersede paths pass `new=None`, so "D-0050 replaces D-0042"
  cannot be rendered.
- **Gating against tombstones false-denies.** After Postgres, then Mongo, then the user's `SUPERSEDE D-0002: back
  to Postgres`, the D-0001 tombstone would deny the user's own revert.

The one real gap is a user supersede whose extraction emits no replacement entry. Then "MongoDB" exists only in
the supersede reason. Nobody has measured how often that happens.

## Second round: review of the finished diff

The fourth reviewer found the gate change sound: nothing else reads `Calibration.calibrated`, and resampling and
`_held_user_flags` use the capped tau. It reproduced three defects in the rest, each now fixed with a regression
test:

1. **The rebuild notice missed weakening without retirement.** A forged `entry_update` that set the provenance to
   agent or narrowed the scope left the rule active, and the notice said "No user rule was left inactive". The
   replay now records, before applying each event, any supersede, status change or update of provenance, scope,
   statement, falsifiers, status or type on an entry that has user authority at that moment. The reassuring
   sentence is gone.
2. **A forged retirement could hide behind older legitimate ones.** The list was ordered by id and capped at 20.
   It is now newest first, capped at 12 with a count of older ones.
3. **The in-process check was easy to bypass, and it refused ordinary work.**
   - Bypasses: `import os, epistemic_monitor.store as s`, `__import__`, `from epistemic_monitor . store`, a
     positional `"user"`, and `getattr`.
   - False refusals: `grep -rnE 'import epistemic_monitor|by="user"'`, a `git commit -m` that says so, and a
     heredoc that writes a test file.

   Detection now needs an interpreter invocation and accepts any `"user"` literal. The import pattern covers those
   forms. A script file, base64 or a variable still get past it. It is documented as a speed bump.

Accepted limits:

- `--min-labels` counts samples, not labels, so one gate record can add up to six. With the cap in place this can
  only make user rules stricter.
- `click.confirm(` next to the import gets an advisory, but is not refused.
